# Sending a Party — the letter, the send, the gifts

The single entry point: right-click a table with the invitation letter, the spread is scanned, the roster is drawn and frozen, and the guests are admitted one a second from the party that opens. Every rejection happens before the letter is consumed, so a refused send costs nothing.

## 1. The invitation letter

A paper item. "Use paper texture for now" — the model points straight at vanilla's, so swapping in a real texture later is a one-line change.

```java
// init/registrate/GLItems.java
INVITATION_LETTER = reg.item("invitation_letter", InvitationLetterItem::new)
        .model((ctx, pvd) -> pvd.generated(ctx, pvd.mcLoc("item/paper")))
        .properties(p -> p.stacksTo(16))
        .lang("Invitation Letter").register();
```

Right-click a `party_table`:

```java
@Override
public InteractionResultHolder<ItemStack> useOn(UseOnContext ctx) {
    var level = ctx.getLevel();
    var pos = ctx.getBlockPos();
    if (!level.getBlockState(pos).is(GLTagGen.PARTY_TABLE)) {
        return InteractionResultHolder.pass(ctx.getItemInHand());
    }
    if (!(ctx.getPlayer() instanceof ServerPlayer sp)) {
        return InteractionResultHolder.success(ctx.getItemInHand());
    }
    return PartySend.send(sp, pos, ctx.getItemInHand());
}
```

`useOn` rather than `use`, so the letter must be aimed at a table and cannot be fired into the air. Mirrors how `TableDecoBlock` and `CoverableImpl` gate their interactions.

## 2. `PartySend.send` — the single entry point

In order:

1. `PartyArea.scan(level, clicked, GLModConfig.SERVER.partyScanDistance.get())` (area.md §2).
2. **Reject** if `food.isEmpty()` — "there is no food on the table".
3. **Reject** if `seats.isEmpty()` — chairs are a hard requirement, so no chairs means no party at all, and the player is told to put some out.
4. **Reject** if `existingParty(level, touchedChunks(food))` is non-`IDLE` (area.md §4) — "there is already a party here".
5. Build the candidate pool: every entity type in `Registries.ENTITY_TYPE` that has a `party_taste` entry, scored by `PartyMath.weight` against the player's reputation read via `CharDataHolder.getUnbounded(sp, type).data().reputation`.
6. `PartyPlanner.select(pool, area.appeal(), area.seats().size())`.
7. **Reject** if the roster is empty — the reason is the highest-scoring near-miss, so the player gets "Reimu would come, but the spread is too plain" rather than a bare failure.
8. Freeze the roster and counters into `GLMeta.PARTY` on the chunk holding `center(food)`, set phase `GATHERING`.
9. Consume one letter (unless creative) and play the send sound.

Every rejection happens **before** the letter is consumed, so a refused send costs nothing.

## 3. Guests

Spawned as temporary clones, exactly as `VisitScheduler.spawn` does (`VisitScheduler.java:71`), and for the same reason: **do not touch `HomeModule`**. With no home binding the clone never receives a `HOME` memory, so the entire sleep and bed subsystem stays unreachable, and the real resident keeps living her ordinary day at home.

```java
public static YoukaiEntity spawn(ServerLevel level, UUID host, BlockPos table, ChunkPos partyChunk,
        EntityType<?> type) {
    if (!(type.create(level) instanceof YoukaiEntity youkai)) return null;
    var module = youkai.getModule(PartyModule.class);
    if (module.isEmpty()) return null;
    youkai.setPos(arrivalNear(level, table, youkai));   // guest.md §2.1: on the ground, near the party, never in the furniture
    youkai.initSpellCard();
    youkai.restrictTo(table, GLModConfig.SERVER.partyGuestRadius.get());
    module.get().arrive(host, table, partyChunk);
    level.addFreshEntity(youkai);
    return youkai;
}
```

`PartyModule` must be in **every** character's module list. The base `YoukaiEntity.createModules()` (`YoukaiEntity.java:224`) is overridden by `CirnoEntity` (`:139`) and `AliceEntity` (`:72`), so the module goes into all three lists, not just the base.

**A send does not spawn anybody on the spot.** It freezes the roster and opens the party; the guests are admitted from there, one a second, wherever they appear (guest.md §2.1). The two exceptions to "a clone" are also guest.md §2's: a character already on site comes as herself rather than as a second copy of her, and a guest with nowhere to sit is told so before she gives up.

## 4. Gifts

**One loot table per character, at `<namespace>:party_gift/<entity type path>`** — `gensokyolegacy:party_gift/cirno`, `.../hakurei_reimu` and so on — generated by `init/data/loot/GiftLootGen.java`. A datapack replaces one by shipping its own file at the same path, and a character with no file of her own falls back to `party_gift/default`. This replaces a weighted draw rebuilt out of the item registry at the moment she leaves, where what she gave was an accident of which items happened to carry a `gift_data` entry.

The fallback is resolved through `ReloadableRegistries`' `lookup` rather than the registry itself, because the reloadable registries answer `LootTable.EMPTY` for a table that was never defined — indistinguishable from a table authored to give nothing, and only the first of the two wants the default ladder.

```java
public static boolean give(ServerLevel level, YoukaiEntity guest, PartyModule party) {
    var loot = tableOf(level, guest);                       // her table, or party_gift/default
    var params = new LootParams.Builder(level)
            .withParameter(LootContextParams.THIS_ENTITY, guest)   // what AppealConsumedCondition reads
            .withParameter(LootContextParams.ORIGIN, Vec3.atCenterOf(table.above()))
            .create(LootContextParamSets.ADVANCEMENT_REWARD);
    loot.getRandomItems(params, stacks::add);
    Block.popResource(level, table.above(), stacks.getFirst());     // one gift, ever
}
```

The generosity comes from **the appeal she personally consumed**, and it comes from *the data* rather than from arithmetic in `PartyGift`. Every table is a **ladder of pools, one per generosity rung**, each one roll, and what an under-served guest is short of is not count — **a gift is always exactly one item** — but *reach*. The ladder is picked by the new `gensokyolegacy:appeal_consumed` loot condition, which reads `PartyModule.appealEaten` off `THIS_ENTITY`. Anything else in that slot — no entity, or a guest with no `PartyModule` — reads as **zero appeal rather than throwing**, so a table whose whole ladder is gated degrades into a table that gives nothing instead of a crash inside somebody's party.

The condition carries `min` and `max`, so it is a **band** rather than a floor, and it reads them as

```java
appeal >= min && (max <= 0 || appeal < max)      // max is EXCLUSIVE; max <= 0 means "no ceiling"
```

**`max` is exclusive, and `max <= 0` is the open-ended sentinel.** Bands are written to tile the appeal range with no gap and no overlap — `[0, 50)`, `[50, 100)`, `[100, 200)`, `[200, ∞)` — so exactly one pool ever answers a roll, whatever the host put out.

```json
{"rolls": 1.0, "conditions": [{"condition": "gensokyolegacy:appeal_consumed", "min": 100, "max": 200}],
 "entries": [{"type": "minecraft:item", "name": "gensokyolegacy:iron_dagger", "weight": 10}]}
```

Four things follow from gating at the *pool*:

- **One item, whatever the table says.** Exactly one band matches, so exactly one pool runs its single roll. `PartyGift` still keeps only `stacks.getFirst()`, so a datapack that ungates two of the pools buries one of them — the mistake stays in the data.
- **A band is exclusive, not a floor.** She does not keep everything the lower rungs would have given her; the ladder moves *up* to what she actually wants rather than widening into everything the host could afford. A lavish banquet narrows the draw to the good gifts, which is both what "generous" reads as to the player and cheaper to compute.
- **The gate is one test per pool, not one per entry.** With the floor shape every entry in the table re-tested its condition on every roll, to decide which ones dropped out; now a pool that fails costs one test and is never expanded.
- **Rungs are set per character, not on a global step size.** There is no `TIERS × APPEAL_PER_TIER` arithmetic any more: a rung is written `tier(min, max, …)` and means whatever the author put there. A guest's own `appealEaten` is a handful of dishes at `nutrition × 0.5 + saturation × 2 + 4` per beneficial effect (food.md §1), so it runs to tens, not units — and how many rungs of that she needs is a statement about how much she eats and how steeply her tastes run out, which one constant cannot carry. `APPEAL_PER_TIER` and `TIERS` survive in `GiftLootGen` as the numbers the bands were first derived from; nothing reads them.

### The ladders

| character | rungs (appeal) | her own stock, and where it sits |
|---|---|---|
| Reimu | 0–50, 50–100, 100–200, 200+ | five of the six talismans over the top two rungs, from `#gensokyolegacy:talisman`, the tag her shop trades from. The folded paper one stays — it is the cheapest of the six and she has no use for it |
| Marisa | 0–50, 50–100, 100–200, 200+ | six of the nine hexbrew bottles, split over the top two. The two she keeps are `WITCH_HEXBREW` and `WITCH_SPLASH` — those are her staff, and she is not handing it over |
| Cirno | 0–20, 20–40, 40+ | the three frozen frogs already on the middle rung, the fairy ice crystal on the top. The shortest ladder in the game: she eats least, so she climbs it fastest |
| Sakuya | 0–50, 50–100, 100–400, 400+ | the iron dagger, then the dagger glove. The wide rung is 300 of appeal because it holds a single item, and a band as narrow as the ones below it would be walked past in one sitting |
| Alice | 0–50, 50–100, 100–400, 400+ | the doll lance, then a doll — she gives up a doll, not the star wand |
| Morichika | 0–50, 50–100, 100–200, 200+ | his stock, split by what it is: the curios (`strange_glasses`, `cat_bell`, `mermaid_pearl`, `straw_hat`) then the tools (`mini_hakkero_prototype`, `centipickaxe`, `dowser`). He has no belongings of his own, only stock |
| *default* | 0–50, 50–100, 100–150 | *(none)* — an unlisted character has nothing that is hers, so her ladder is three generic rungs and stops there |

**The whole ladder is on the page.** A gift is otherwise invisible until it happens, and a host who cannot see the rungs cannot lay a spread that reaches one. JEI has a page per character (`PartyGiftCategory`), one row per rung with the appeal band that reaches it, and each gift's chance of being drawn in the slot tooltip. Loot tables are not synced, so the server reads every ladder on a datapack sync and sends it (`PartyGiftToClient`), keyed by entity type — the `party_taste` rows are the roster, so those and only those characters have a page, and one with no table of her own gets the fallback ladder on hers.

**Her own stock.** Each character parts with something that is actually hers, or at least what only she has. It is a *selection within* the top rungs rather than a block of its own, and the table above doubles as the record of what was deliberately left out — Marisa's staff, Alice's star wand, Reimu's folded paper talisman.

Two consequences of that shape are worth stating. Her own items **are** the top one or two rungs and the generic spread sits beneath them, so the top of a well-fed character's ladder is entirely her own rather than her own diluted against bottles of sake. And where one item spans two rungs it is **halved on the upper one** (Reimu's lava talisman, Cirno's frogs, 10 → 5), which is how the same object reads as "she is willing" and then as "she really is" without the ladder needing another rung for it.

The own-stock entries are at 10 throughout, against 10..40 for the generic items. But a rung holds **either** own stock **or** generic and never both, so a weight has nothing to be more or less frequent than — "the band already decided she may, this only decides how often" no longer means anything. Where a rung mixes two generics it still tilts the draw (Reimu's teddy bear at 40 against two sakes at 20); where it holds only her own, every weight is equal and the draw is flat.

The pools are written out rather than read from their tags. A loot entry can only name one item, so a tag has to be expanded at datagen either way — and the datagen holder lookup hands back tags that are still being constructed (`HolderSet.emptyNamed`, whose `contents()` throws). The table is what ships, so the list is what has to be right.

What all this is sized on is deliberately *not* whether she was satisfied. Those are two of the three food measurements (select.md §2.1) and they answer different questions: rare-effect delicacies fill her up no better than plain bread, and she is still more moved by them. An earlier version halved the gift for an under-served guest, which made a beautiful thin spread read as stingy rather than as modest; the host's generosity and the guest's appetite are not one axis.

`GLMeta.GIFT_PREFERENCE` still exists and still weights categories per character, but only on the *incoming* path — `GiftModule` scoring a gift handed **to** her, and its tooltip. The outgoing gift does not read it at all: what a character gives is written into her ladder by hand, so the same numbers that once came out of a data map are now baked into `GiftLootGen`. The two can drift apart, and nothing catches it.

`Block.popResource` at the table is the in-tree idiom for putting an item down in the world (`MarisaTaskUtil.java:94`, `ShelfBlockEntity`). That matches "thrown on table for now" exactly, and because nothing is granted into an inventory there is nothing to unwind when the real gift item is designed.

**A guest leaves one gift, ever.** She has two ways out — the spread she can reach runs out, or `leaveChance` comes up — and a visit can pass close enough to both that she would otherwise thank the host twice for one banquet. The flag is on `PartyModule` rather than in `PartyGift`, so it survives the two call sites and any task restart between them. A guest with nothing tasteful to give still leaves nothing rather than something arbitrary, as before.

**The host is paid in reputation, once per guest.** Every guest who ate from the party rates it, and the host gains `repGain` of the appeal **she personally consumed**:

```java
int value = taste.reputationFor(appealEaten);   // floor(appealEaten * repGain), at least 1
CharDataHolder.getUnbounded(player, self.getType()).gain(value, 0, 0, 0);
```

Four decisions inside that one line, each of which would be worth arguing about:

- **Her own appeal, not the party's.** This is the same quantity her gift is sized on (§4, one paragraph above) and for the same reason: a host is paid for feeding *her*, not for the size of the table she happened to sit at. Two guests at one party are worth different amounts, and that is the honest reading — a character served a delicacy and left content is a better advertisement for the host than one handed a slice of bread and left because she was still hungry.
- **Appeal, not hunger.** Appeal is what the food was worth; hunger is what it fed. Feeding someone is not the same as impressing them, and select.md §2.1 keeps the two apart everywhere else. `PartyAttachment.appealServed` is still tracked, for `party info`; the payout reads her own tally.
- **Paid at leave, not at close.** A guest who walked out mid-party has still been paid for what she ate. It also means a guest who never ate — expelled for want of a chair — pays nothing, so putting out too few chairs is not a way to farm reputation.
- **Floored at one, never at zero.** This is now load-bearing rather than a nicety: five percent of a guest's own three slices of cake is 0.3, and it would floor to nothing. A rule that pays nothing for an ordinary party is not a rule the host can learn from, and the alternative — scaling `repGain` until small parties pay — would give every character a different meaning for the same number. It costs nothing, because `gainReputation` refuses to move a reputation that is already at its cap anyway.

Nothing is paid to a host who has logged off or changed dimension — the same rule as the party's messages, and for the same reason: there is no queue of things that happened while they were not here.

**There is no cooldown.** Reputation is read once, at send, to decide the roster, and the party never spends it — there is no loss anywhere in the system. The letter names no character, so there is nothing to rate-limit; a repeated send simply draws again, and an unsuccessful one fails the same way.
