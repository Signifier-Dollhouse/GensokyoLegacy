# Hats

`TouhouHatItem` — the touhou hats worn in the vanilla head armor slot and the curios head slot.

> Status: implemented. Five hats: straw, suwako, suwako straw, frog straw and koishi. Four are
> drawn as `ModelPart` models; koishi carries its geometry as a vanilla model file (§2).

A hat is a plain `Item implements Equipable, ICurioItem` — *not* an `ArmorItem`. Vanilla's
`HumanoidArmorLayer` only draws `ArmorItem`s, so the head slot is covered by
`TouhouHatLayer`, an entity layer swept onto every `LivingEntityRenderer` with a `HumanoidModel`
(`GLClient.addCharacterLayers`). The curios head slot reuses the same code through
`TouhouHatRenderer.renderHat`. The `Equipable` half makes the vanilla head slot accept the stack;
`ICurioItem` covers curios, and the vanilla slot additionally ticks the item (`inventoryTick`).

## 1. ModelPart hats

The default path. The hat supplies a `ModelLayerLocation` through
`IClientItemExtensions.getHumanoidArmorModel` and a texture through `getArmorTexture`;
`TouhouHatRenderer` copies the wearer's `setupAnim` pose onto it and draws it. The layer definitions
live in `content/client/model/` (`SuwakoHatModel`, `FrogStrawHatModel`) and are registered in
`GLClient.registerLayerDefinitions`; `GLItems` wires each item to its layer with
`.clientExtension(() -> () -> new HatModel(...))`.

`FrogStrawHatModel` shows the pattern worth copying for a biped: `createBodyLayer()` builds the
*frog's own* mesh, and `createHat()` grafts the hat onto that frog's `head` part, because
`HumanoidArmorLayer` and friends expect the root to carry named parts. For a biped hat
`HumanoidModel.createMesh` is the equivalent body.

## 2. Modeled hats

A hat returns `true` from `isModeledHat()` when its geometry should be an item model rather than a
`ModelPart` model. `KoishiHatItem` is the only one, and it draws through `HeadItemRenderer` exactly
like the strange glasses.

The reason is UV control, not taste. `ModelPart` is `final` and `ModelPart.Cube` lays its faces out
in the fixed vanilla box unwrap, so `CubeListBuilder.addBox` can only ever place a face at one
derived offset from `texOffs`. Blockbench exports give every face its own explicit UV rect and may
rotate an element about a pivot outside it — neither is expressible, so the geometry has to be a
vanilla model file.

### How it is wired

Three pieces, mirroring `StrangeGlassesItem` / `StrangeGlassesRenderer`:

- `models/custom/koishi_hat_head.json` — the geometry, a Blockbench *Java Block/Item* export with
  face UVs based on a 16×16 grid. It samples `textures/item/curio/koishi_hat_head.png`, alongside
  the icon rather than under `textures/model/`, so it lands in the atlas like the glasses' head
  texture; the `textures/model/` folder is for the `ModelPart` hats, which are drawn off a
  `RenderType` rather than a model.
- `models/item/koishi_hat.json` — generated by `SeparateTransformsModelBuilder`: a
  `neoforge:separate_transforms` model whose `base` is the flat 16×16 icon and whose `head`
  perspective is a parent pointing at the geometry file. So the inventory shows the icon and the
  head slot shows the hat.
- `HeadItemRenderer.render` — snap to the head bone, `CustomHeadLayer.translateToHead`, then
  `ItemInHandRenderer.renderItem(..., ItemDisplayContext.HEAD, ...)`. Vanilla applies the model's
  own head transform, its texture and the block centring, so none of that is re-implemented here.

`HeadItemRenderer` is shared with `StrangeGlassesRenderer`, which is curios-only: the glasses need
no entity layer because `CustomHeadLayer` already draws a non-armor helmet-slot item on players. The
koishi hat still needs `TouhouHatLayer`, because that layer is what covers humanoids vanilla does
not give a `CustomHeadLayer`.

### Editing the koishi hat

`models/custom/koishi_hat_head.json` is a Blockbench *Java Block/Item* export: 0-16 block space, and
the face UVs are based on a 16×16 grid whatever `texture_size` claims in the file. Nothing in the
export needs correcting, so a re-export drops straight in. The only edits on import are the ones
that make it a loadable vanilla model: the `textures` block, a `minecraft:block/block` parent, and
zero-angle `rotation` blocks kept as Blockbench writes them so a re-export diffs clean.

`display.head` is left exactly as Blockbench wrote it. Vanilla reads the translation in *model*
units — `ItemTransform.Deserializer` multiplies it by 0.0625 — and the scale as a plain factor, so
`[0, 4.7, 0]` and `scale 1.65` are already in the right units and were tuned against the head
preview. Do not rescale them by hand.

Element 0 in the model is a second, slightly smaller copy of the crown that sits entirely inside
element 3. It is harmless and was left in so the file still matches what Blockbench exports.
